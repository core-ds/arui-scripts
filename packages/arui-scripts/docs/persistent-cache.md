# Постоянный кэш Rspack

Кэш сохраняет промежуточную работу на диске и использует ее при следующем запуске `start`, `start:prod` или `build`. Это особенно полезно при повторных запусках dev и восстановлении кэша в CI. Итоговая сборка всегда создается заново; кэш не заменяет `.build` и проверку типов.

По умолчанию функция выключена: dev использует прежний кэш в памяти, production собирается без постоянного кэша.

```ts
// arui-scripts.config.ts
import type { PackageSettings } from 'arui-scripts';

export default {
    persistentCache: true,
} satisfies PackageSettings;
```

По умолчанию данные хранятся в `<project>/.cache/arui-scripts/rspack`. Добавьте `.cache/arui-scripts/` в `.gitignore` приложения
и в `.prettierignore`, если форматтер обходит все JSON-файлы проекта. Кеш не попадает в очищаемую папку сборки.
В dev его изменения игнорируются watcher.

## Настройки

Вместо `true` можно передать объект:

```ts
persistentCache: {
    modes: ['dev', 'production'],
    directory: '.cache/arui-scripts/rspack',
    version: 'my-pipeline-v1',
    buildDependencies: ['./build-values.json'],
    env: ['MY_COMPILE_FLAG'],
    portable: false,
    readonly: false,
}
```

| Поле                | Значение и назначение                                                                                                                                                         |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `modes`             | Непустой массив `dev` / `production`. По умолчанию оба.                                                                                                                       |
| `directory`         | Путь от корня приложения или абсолютный путь к отдельному каталогу кэша. Нельзя использовать корень диска, каталог проекта, `node_modules`, buildPath или пути через symlink. |
| `version`           | Добавка к автоматической совместимости. Измените ее, если изменилось поведение внешнего инструмента, которое невозможно отследить файлом или переменной.                      |
| `buildDependencies` | Дополнительные существующие файлы/каталоги, которые читает ваш override/plugin. Неверный путь вызывает ошибку настройки.                                                      |
| `env`               | Имена дополнительных переменных, влияющих на компиляцию. Значения учитываются в хэше и не печатаются в `cache:info`. Не перечисляйте здесь обычные runtime-переменные.        |
| `portable`          | Переносимый формат Rspack. В версии 2.2.5 при смене абсолютного пути проекта первая сборка пересчитывается, чтобы избежать устаревших путей модулей и source maps.            |
| `readonly`          | По умолчанию `false`. Читать имеющийся native-кэш, не сохранять изменения. Отсутствие кэша приводит к полной сборке.                                                          |

Автоматически учитываются настройки arui, окончательная конфигурация обработки и выходов, Node/ОС/архитектура, app/package/lock-файлы в родительских workspace, конфиги TS с `extends`, browserslist, presets/overrides и их обычные импортируемые зависимости, theme и словари сжатия. Изменения установленного кода arui тоже инвалидируют кэш. Локальные linked-пакеты проверяются как изменяемые файлы.

Произвольный plugin может читать файлы динамически или захватывать переменные из окружения. Его автор должен перечислить такие входы через `buildDependencies`, `env` или `version`. Экземпляры plugin не сериализуются. Если остальные настройки невозможно безопасно fingerprint-ить, arui выводит предупреждение и собирает с прежней стратегией кэша.

Client/server, режимы, имена, входы/выходы и профили обработки изолированы. Порядок конфигураций в массиве не влияет на область хранения. Низкоуровневое переопределение `rspackConfig.cache` имеет приоритет: такой кэш помечен `custom`, его путь и очисткой управляет автор override.

В dev для clientOnly runtime `env-config.json` генерируется заново при новом процессе с текущим окружением. Production сохраняет прежний контракт подстановки окружения при запуске приложения. Runtime-значения не включаются в compile-time fingerprint автоматически.

## Диагностика и очистка

```sh
yarn arui-scripts cache:info
yarn arui-scripts cache:info --json
yarn arui-scripts cache:clear
```

Info показывает путь, режимы, размер сохраненных данных, namespaces, fingerprint и политику текущих конфигураций (`arui` / `custom` / `legacy`). Ни содержимое настроек, ни значения env не выводятся.

Clear удаляет данные только из каталога с marker владения arui-scripts. Сохраняет build output, `node_modules` и другие кэши. Отсутствующий кэш считается уже очищенным. Clear откажется работать при активной сборке, symlink внутри каталога или отсутствии marker. Сначала остановите dev/build. Если другой процесс уже пишет в ту же область, новая сборка выдаст предупреждение и продолжит без постоянного кэша.

При недоступном для записи каталоге сборка продолжится с предупреждением. Поврежденные native-данные Rspack восстанавливает пересборкой. Ошибки кода и проверки типов продолжают завершать сборку с ошибкой.

## Jenkins: восстановить → собрать → сохранить

1. Установить зависимости согласно lock-файлу.
2. Восстановить `.cache/arui-scripts/rspack` средствами CI.
3. Выполнить обычную команду сборки.
4. После завершения сохранить тот же каталог в cache-хранилище CI.
5. `.build` сохранить отдельно как артефакт результата.

В cache key CI включите проект, ОС/архитектуру, Node, версию arui и hash lock-файла. Для ускорения на Rspack 2.2.5 сохраняйте одинаковый абсолютный путь checkout. При смене пути первая сборка пересчитывается, включая режим `portable: true`: проверка обнаружила старые пути модулей/source maps в native portable-восстановлении. Следующие сборки в новой папке используют кэш. Разные проекты не должны делить один каталог. Не восстанавливайте и не сохраняйте его во время работы компилятора.

Arui сохраняет кэш при штатном завершении: build ждет `compiler.close()`, dev сначала останавливает сервер/watch, затем закрывает compiler. Parent-процесс ждет остановки дочерних компиляторов. Для dev установлен предел 10 секунд; повторный сигнал завершает процесс принудительно. После SIGKILL/падения ОС сохранение не гарантируется.

### Пример для Job Cacher

Следующий фрагмент предназначен для Linux-агента и требует установленного
[Job Cacher](https://plugins.jenkins.io/jobcacher/). Наличие плагина в вашей Jenkins-инсталляции нужно проверить.
Если кешированием управляет Jenkins Shared Library, используйте ту же последовательность в ней.

```groovy
stage('Build') {
    steps {
        sh 'yarn install --immutable'
        script {
            def platform = sh(returnStdout: true,
                script: 'node -p "process.platform + \'-\' + process.arch"').trim()
            def nodeVersion = sh(returnStdout: true, script: 'node --version').trim()
            def aruiVersion = sh(returnStdout: true, script: 'yarn arui-scripts --version').trim()
            def lockHash = sh(returnStdout: true, script: 'sha256sum yarn.lock | cut -d " " -f 1').trim()

            cache(maxCacheSize: 1024, caches: [arbitraryFileCache(
                path: '.cache/arui-scripts/rspack',
                cacheName: "rspack-${platform}-${nodeVersion}-${aruiVersion}-${lockHash}",
                includes: '**/*',
                excludes: '**/.writer.json,**/.operation.lock',
                useDefaultExcludes: false
            )]) {
                sh 'yarn arui-scripts build'
            }
        }
    }
}
```

В конфигурации приложения должно быть `persistentCache: true` (либо объект с `modes: ['production']`).
Job Cacher восстанавливает каталог перед блоком и сохраняет после его выполнения; настройка `cacheValidityDecidingFile`
здесь не используется, чтобы обновленная компиляция сохранялась и при неизменном lock-файле.
Плагин изолирует кеши по job; при собственном хранилище добавьте в ключ также идентификатор проекта/job.
Не давайте параллельным сборкам один живой каталог: каждая сборка работает со своей восстановленной копией.
Каталог `.build` публикуется отдельно средствами существующего pipeline.

Диагностические сборки `bundle-analyze` и сборки с `ARUI_SCRIPTS_RSDOCTOR_OUTPUT` выполняются без постоянного кеша,
чтобы профилировщик собирал свежие данные обо всем графе модулей.

## Проверка разработчиком arui-scripts

После сборки пакетов:

```sh
node packages/arui-scripts/test/persistent-cache.cjs
node packages/arui-scripts/test/persistent-cache-lifecycle.cjs
```

Каждый build fixture запускается отдельным процессом. Проверяется подтвержденное native-восстановление, совпадение ассетов со сборкой без кэша, инвалидация входов и перенос checkout. Время печатается для диагностики: небольшой fixture не является прогнозом ускорения большого приложения.

Lifecycle-проверка запускает настоящий dev-сервер и серверный watcher, отправляет SIGTERM родительскому процессу и проверяет завершение дочерних процессов и сохранение кэша. Ей требуется доступ к локальному порту.
