# React-хелпер для mountable-модулей

## Цель

Заменить ручные реализации `mount`, `hydrate`, `update`, `unmount` для React-модулей
готовым адаптером с изоляцией экземпляров и поддержкой lifecycle context первого этапа.
Хелпер реализуется поверх существующего контракта; изменения API хоста не требуются.
Комментарии, документация и описания новых тестов пишутся на русском языке.

## Публичный API

Отдельная точка входа `@alfalab/scripts-modules/react` экспортирует
`createReactModule`, `useModuleReady` и тип `ReactModuleProps`.

```tsx
import {
    createReactModule,
    useModuleReady,
    type ReactModuleProps,
} from '@alfalab/scripts-modules/react';

type RunParams = { accountId: string };

function App({ runParams, serverState }: ReactModuleProps<RunParams>) {
    const data = useAccount(runParams.accountId, serverState.preloadedState);

    useModuleReady(data.status === 'success');

    return <AccountScreen data={data} />;
}

export default createReactModule({
    Component: App,
    readiness: 'explicit',
});
```

`useAccount` и `AccountScreen` в примере принадлежат приложению, а не библиотеке.

```ts
type ReactModuleProps<
    RunParams = void,
    ServerState extends BaseModuleState = BaseModuleState,
> = {
    runParams: RunParams;
    serverState: ServerState;
};

createReactModule<RunParams, ServerState>({
    Component,
    readiness?: 'auto' | 'explicit',
}): MountableModule<RunParams, ServerState>;

useModuleReady(condition?: boolean): void;
```

`Component` типизируется как React-компонент с `ReactModuleProps`. По умолчанию
готовность автоматическая, `condition` по умолчанию равен `true`.
Дополнительные настройки root, собственного fallback, StrictMode и преобразования
props в первую версию не входят. Провайдеры приложения размещаются внутри `App`.

## Выбор подхода

Рекомендуется `Component` с фиксированными props и React-хук готовности. Он оставляет
бизнес-логику в обычном React-компоненте и не смешивает lifecycle context с props.
Альтернативы: render-функция фабрики, получающая context, или дополнительный callback
готовности в props компонента. Первая требует ручного управления сигналами рядом с
рендером, вторая распространяет служебные props через дерево. В первой версии
реализуется только рекомендуемый вариант.

## Готовность

Хелпер всегда возвращает `readiness: 'explicit'` в контракте MountableModule, включая
режим `auto`. Поэтому новый mounter не считает возврат из `root.render()` готовностью.
Настройка `readiness` самой фабрики определяет, кто отправляет явный сигнал.

- `auto`: внутренний React-компонент отправляет сигнал после первого успешного commit.
- `explicit`: сигнал отправляет `useModuleReady(true)` после commit компонента,
  вызвавшего этот хук. Пока condition ложен, ожидание продолжается.
- Вызов хука во время рендера не вызывает `reportReady`: используется эффект.
- Готовность одноразовая на запуск экземпляра. Изменение condition обратно в false
  и последующие update не сбрасывают её. Если хук вызван несколькими компонентами,
  достаточно первого истинного сигнала; объединять несколько условий должен сам модуль.
- Сигналы доставляются в микрозадаче после React-эффектов с повторной проверкой,
  что запуск активен и не завершился ошибкой. Это позволяет callback-у хоста безопасно
  инициировать cleanup и не сообщает готовность после ошибки того же commit.
- Без внешнего context модуль продолжает рендериться; уведомления хоста отсутствуют.
  `useModuleReady` вне внутреннего Provider тоже ничего не делает, например в Storybook.
- В режиме auto вызов useModuleReady не меняет автоматическую семантику.

Первый commit может содержать Suspense fallback или индикатор загрузки самого
приложения. Хелпер не определяет бизнес-готовность по содержимому UI. Для неё требуется
explicit-режим и условие, выбранное приложением. Хелпер не добавляет собственный
Suspense fallback; его определяет приложение.

## Lifecycle и несколько экземпляров

Адаптер хранит отдельную запись root для каждого targetNode внутри фабрики.
`mount` создаёт root через `createRoot`, `hydrate` — через `hydrateRoot`,
`update` вызывает `root.render` с актуальными runParams и serverState.
Контекст запуска хранится отдельно от props; все обновления используют тот же
запуск, Provider и Error Boundary, сохраняя React-состояние компонентов.

Повторный mount/hydrate в уже активный контейнер выбрасывает понятную ошибку.
Update до mount/hydrate тоже выбрасывает ошибку. Повторный unmount безопасен.
Unmount делает запуск неактивным синхронно, чтобы отменить отложенные уведомления.
Освобождение React root откладывается до микрозадачи: хост может вызвать cleanup
во время собственного React commit, когда синхронный root.unmount небезопасен.

Если тот же targetNode запускается повторно до отложенного освобождения,
используется существующий root, отложенное уничтожение отменяется, а ключ дерева
меняется для создания нового экземпляра приложения без сохранения старого состояния.
Это предотвращает создание двух root в контейнере и удаление нового дерева старым
cleanup в StrictMode. После фактического уничтожения запись удаляется.
Записи разных контейнеров, контексты, сигналы и ошибки независимы.

## Ошибки

Внутренний Error Boundary охватывает приложение и компоненты готовности. Он сообщает
фатальные ошибки React-дерева через `context.reportError`, включая ошибки обновлений.
После ошибки Boundary возвращает null; fallback и состояние ошибки определяет хост.
Отправка ошибки откладывается до микрозадачи, чтобы mounter не размонтировал root
синхронно внутри componentDidCatch. Готовность после ошибки запрещена.

Ошибки синхронного создания root пробрасываются из mount/hydrate; mounter уже умеет
классифицировать их по этапу. Повторная отправка той же фатальной ошибки исключается
на уровне запуска. Без внешнего context Boundary выводит ошибку в console.error.

Ошибки обработчиков событий и произвольных фоновых Promise не перехватываются
Boundary автоматически. В первой версии для их интеграции можно пользоваться
обычным контрактом ModuleLifecycleContext при собственной обёртке адаптера; отдельный
универсальный хук доступа к контексту в эту задачу не входит.
Восстановимые ошибки гидрации не считаются фатальными: сохраняется стандартное
восстановление React. Автоматическое преобразование hydration mismatch в reportError
не добавляется.

## Пакет и совместимость

Новая точка входа имеет CommonJS, ESM и declarations, а также запись typesVersions
по аналогии с существующим `/ssr`. Основная точка входа не импортирует react-dom/client.
Добавляется опциональная peer-зависимость `react-dom >=18`: она необходима при
использовании `/react`. Для хелпера нужны согласованные версии React и ReactDOM 18+;
требования существующего основного API к React не ужесточаются.
Хелпер не обращается к document и не создаёт root при импорте или вызове фабрики.
Серверный рендеринг React-компонента приложения остаётся у сервера модуля; хелпер
предоставляет клиентскую гидрацию, а не отдельный серверный render API.

## Проверка и документация

Тесты на настоящем React root проверяют mount, hydrate с сохранением серверного DOM,
update с сохранением React-состояния, несколько контейнеров, повторный unmount,
перезапуск в тот же контейнер, StrictMode и отсутствие предупреждений о вложенной
очистке root. Проверяются автоматическая и явная готовность, condition false/true,
повторы, поздние сигналы, отсутствие context и хук вне Provider. Проверяются ошибки
начального рендера и update, подавление готовности после ошибки и связка с реальным
mounter. Проверяется импорт новой точки входа в обеих сборках и экспорт типов.

В документацию добавляются простейший auto-модуль, explicit-пример с данными,
требования к версиям, семантика Suspense и границы Error Boundary.
Один существующий пример React-модуля переводится на хелпер, чтобы показать
замену ручного lifecycle. Добавляется minor changeset.
