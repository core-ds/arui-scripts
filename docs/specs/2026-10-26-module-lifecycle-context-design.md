# Опциональный lifecycle context модулей

## Цель и границы

Дать хосту события готовности и ошибки конкретного экземпляра mountable-модуля без
подмены методов его экспорта. Существующие модули продолжают работать без изменений.
Первый этап включает контракт и поддержку во всех клиентских mounter-ах библиотеки:
`useModuleMounter`, `createLazyMounter`, клиентская часть `createSsrMounter`.
React-хелпер `createReactModule` и React-хуки готовности относятся ко второму этапу
и в эту реализацию не входят. Серверный рендеринг и его протокол не меняются.

## Контракт модуля

```ts
export type ModuleLifecycleContext = {
    signal: AbortSignal;
    reportReady(): void;
    reportError(error: unknown): void;
};

export type ModuleMountFunction<RunParams, ServerState> = (
    targetNode: HTMLElement,
    runParams: RunParams,
    serverState: ServerState,
    context?: ModuleLifecycleContext,
) => void | Promise<void>;
```

Одинаковая сигнатура используется для `mount`, `hydrate`, `update`.
`unmount(targetNode, context?)` получает контекст снимаемого запуска, чтобы модуль
мог отличить его от другого владельца того же контейнера. Вызов без контекста
сохраняет прежнее поведение. Контекст опционален в типе:
новый модуль может работать со старым хостом, используя `context?.reportReady()`.
Новый mounter всегда передаёт контекст. Старые трёхаргументные реализации совместимы.

В `MountableModule` добавляется `readiness?: 'explicit'`.

- Без свойства готовность наступает после успешного завершения `mount` или `hydrate`,
  включая ожидание возвращённого Promise. Это не гарантия React commit.
- При `readiness: 'explicit'` дополнительно требуется `reportReady()`.
- Сигнал, полученный внутри `mount` до его завершения, запоминается; `onReady` вызывается
  только после успешного завершения метода. Последующий throw/rejection отменяет готовность.
- Готовность одноразовая на запуск экземпляра. `update` не сбрасывает её и не запускает
  новый таймаут. В режиме без явной готовности `reportReady()` не ускоряет завершение метода.
- `reportError` работает в обоих режимах, в том числе после готовности.

## API хоста

Общие опциональные настройки: `onReady`, `onError`, `readyTimeoutMs`.
`onReady` не принимает аргументов; `onError` принимает объект `{ error, stage }`.

Для `useModuleMounter` настройки передаются в аргумент хука; для `createSsrMounter`
в props `ModuleComponent`; для `createLazyMounter` в настройки фабрики, чтобы не
занимать имена props, которые сейчас целиком принадлежат `RunParams` модуля.
Состояние lifecycle и cleanup всегда принадлежит отдельному смонтированному экземпляру,
даже если фабрика lazy-mounter и её callbacks общие для нескольких экземпляров.

Этапы ошибок: `fetch-manifest`, `fetch-resources`, `resolve-export`, `mount`, `hydrate`,
`update`, `runtime`, `ready-timeout`, `unmount`. Загрузчик должен сохранить сведения
об этапе при передаче ошибки mounter-у, не требуя от потребителя собственных хуков.
`reportError` сообщает ошибку с этапом `runtime`. Ошибки callback-ов потребителя не
классифицируются как ошибки модуля и не запускают повторные lifecycle-уведомления.

Существующие loader hooks сохраняются для совместимости и мониторинга. `onAfterModuleMount`
по-прежнему означает получение экспорта, а не готовность UI. Mounter не меняет методы
экспортируемого модуля. Ошибка одной операции сообщает `onError` экземпляра один раз,
даже если загрузчик уже вызвал свой отдельный monitoring hook.

`readyTimeoutMs` задаётся явно: по умолчанию таймаута нет. Положительное конечное
значение включает его только для `readiness: 'explicit'`; прочие значения отключают.
Отсчёт начинается непосредственно перед вызовом первого `mount`/`hydrate`, а не при
загрузке ресурсов. Готовность, ошибка или cleanup отменяют таймер.

`useModuleMounter.loadingState` остаётся `pending` до готовности, затем становится
`fulfilled`; фатальная ошибка переводит его в `rejected`, включая ошибку после готовности.
SSR и lazy-mounter сообщают состояние callbacks; управление fallback остаётся у хоста.

## Выполнение и освобождение ресурсов

Общая внутренняя реализация управляет запуском экземпляра, чтобы три mounter-а не
расходились в обработке Promise, готовности и cleanup. Она сохраняет получатель `this`
при вызове методов и не изменяет разделяемый экспорт.

Синхронный throw и rejection lifecycle-метода обрабатываются одинаково. Mounter ожидает
завершения первичного метода перед `update`; обновления выполняются последовательно.
Изменения параметров во время первичного запуска не теряются: после его успешного
завершения применяется последнее актуальное значение, если модуль поддерживает `update`.
Прежнее поведение модулей без `update` сохраняется в каждом существующем mounter-е.

Первая фатальная ошибка останавливает новые обновления, отменяет signal и освобождает
экземпляр. Внутреннее состояние меняется до уведомления хоста, чтобы синхронный callback
не вызвал повторную очистку. `module.unmount(target, context)` вызывается один раз, если первичный
lifecycle-метод был запущен, в том числе при частичном неудачном монтировании. Ресурсы
loader освобождаются независимо от ошибки `module.unmount` с сохранением существующего
учёта разделяемых ресурсов lazy-mounter.

При ошибке cleanup исходная ошибка сохраняется; ошибка очистки отдельно сообщается
с этапом `unmount`. При обычном размонтировании ошибка очистки тоже доступна через `onError`.
После остановки сигналы контекста и результаты Promise не меняют состояние и не вызывают
callbacks готовности/runtime-ошибки. Отмена при размонтировании сама по себе не ошибка.
StrictMode создаёт отдельный запуск с новым контекстом; отменённый запуск не может
сообщить готовность следующего. Если асинхронная работа модуля переживает отмену, сам
модуль обязан учитывать signal и не изменять DOM после отмены; хост не может отменить
произвольный Promise.

## Проверка

Регрессионные тесты проверяют старый модуль без контекста, успешные и неуспешные
Promise из lifecycle, автоматическую и явную готовность, ранний и повторный reportReady,
runtime-ошибку после готовности, таймаут только в explicit-режиме, изменение runParams,
изоляцию двух экземпляров, отмену и запоздалые сигналы, StrictMode, очистку частичного
mount, сохранение исходной ошибки при ошибке unmount, освобождение ресурсов.
Интеграционные тесты охватывают каждый mounter и SSR hydrate/fallback mount.
Проверка типов подтверждает совместимость трёхаргументных модулей и опциональность
контекста. Запускаются Jest пакета, обе TypeScript-сборки и проверки форматирования/lint.

## Будущий React-хелпер

Хелпер сможет выставлять `readiness: 'explicit'`, передавать lifecycle context через
внутренний React Provider и реализовать `useModuleReady(condition)` эффектом после
commit. Внутренний Error Boundary будет вызывать `reportError`. Эти компоненты и
окончательный API хелпера сейчас не реализуются.
